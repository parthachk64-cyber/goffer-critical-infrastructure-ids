# Data

Two inputs, kept apart everywhere (README, reports, manifests): a **synthetic demonstration** fixture and an **independent benchmark**.
Nothing here is operational data. All inputs are pre-extracted flow records; no payloads, no live capture.

## Model inputs (both sources)

37 numeric and 3 categorical columns, allowlisted in `src/infra_ids/schema.py`: `dur, spkts, dpkts, sbytes, dbytes, rate, sttl, dttl, sload, dload, sloss, dloss,
sinpkt, dinpkt, sjit, djit, swin, dwin, tcprtt, synack, ackdat, smean, dmean, trans_depth, response_body_len, ct_* (9), is_ftp_login, is_sm_ips_ports`
and `proto, service, state`. Excluded from inputs: `label` (target), `attack_cat` (evaluation only), `id` (becomes an opaque row id), `stcpb` and `dtcpb`
(raw TCP sequence numbers, arbitrary and non-semantic), and any unknown extra column (listed under `ignored_columns` in the manifest).
`assert_no_leakage` and tests enforce this.

Field semantics worth stating (from the dataset's feature documentation): `dur` is flow duration in seconds; `sttl`/`dttl` are time-to-live values;
`sload`/`dload` are bits per second; `sinpkt`/`dinpkt` are inter-packet times in ms; `ct_*` count connections among the last 100 sharing the named
attributes. **`dur` is how long a flow lasted. It does not say when an incident was first detected, and nothing here measures detection time.**
Missing in both sources: timestamps, IPs, ports, payload content. Labels are binary (`label`: 0 normal, 1 attack).

## Synthetic demonstration fixture

`data/fixtures/synthetic_train.csv` (2,000 rows) and `synthetic_test.csv` (1,000 rows), generated by `data/generate_fixture.py` with seed 42
(`src/infra_ids/synthetic.py`). Four scenarios: clean benign, clean attack, **ambiguous benign** (bulk transfers that look like a fan-in burst) and
**ambiguous attack** (a slow probe that looks normal). The signal is built by the generator, so good scores show the pipeline works, not that anything is
detected on a real network. Results from it are always labelled "synthetic demonstration".

- Regenerate and rewrite checksums: `python data/generate_fixture.py` (also rewrites `tests/fixtures/`).
- Verify without writing: `python data/generate_fixture.py --check` (run in CI).
- Checksums: `data/fixtures/SHA256SUMS`.
- Test fixtures in `tests/fixtures/`: `clean_small.csv`, `duplicate_event.csv` (one repeated event id), and four invalid files (missing column, non-numeric value, bad label, negative count).

## Independent benchmark: UNSW-NB15

- **Provider:** UNSW Canberra Cyber, UNSW Sydney. Access instructions and terms: <https://research.unsw.edu.au/projects/unsw-nb15-dataset>.
- **Files used:** the provider's partition CSVs `UNSW_NB15_training-set.csv` (175,341 rows) and `UNSW_NB15_testing-set.csv` (82,332 rows). Row counts match the provider page.
- **Terms (provider page, verbatim):** "Free use of the UNSW-NB15 dataset for academic research purposes is hereby granted in perpetuity. Use for commercial purposes should be agreed by the authors." Redistribution is not stated, so **the data is not redistributed here**. Download it yourself.
- **Citation:** the provider page asks users to cite its listed papers, including Moustafa & Slay, MilCIS 2015, and Moustafa & Slay, *Information Security Journal* 2016.
- **Manual import:** the provider distributes through an external file-sharing folder. Whether it requires an interactive step was not stated on the page; if the download needs one, save the two CSVs anywhere and pass their paths to `benchmark`. Files are never fetched automatically.
- **Limits of transfer:** UNSW-NB15 was generated in a lab testbed with synthetic attack tooling (the benchmark labels nine attack families). Flow statistics from one lab network in one period say little about a power grid, a bank or a ministry. Published scores on it are also known to be sensitive to duplicate records and to how the partitions were built.

### Handling rules this repository applies

- Provider partitions are respected: the testing CSV is only used for the final evaluation.
- A validation split is taken **inside the training CSV** (20%, seeded, group-aware so exact duplicates stay together). Preprocessing statistics, normal-profile statistics, score normalisation and every threshold use fit/validation rows only.
- `label` is the target; `attack_cat` is used only to report per-category results and never as an input.
- Exact duplicates of the model-input columns between training and test partitions are counted in the manifest (`duplicate_overlap`), label disagreement among them is counted, and each report repeats the metrics excluding those rows.

### What the data manifest records

Each run's `manifest.json` stores, for both files: filename, SHA-256, bytes, rows read and kept, duplicate ids dropped, ignored columns, class distribution,
categorical level counts; plus the split sizes, preprocessing description, duplicate overlap, Python and dependency versions and the seed. Feature
transformations: signed log1p then standardisation (training mean/std, clipped at 10), top-20 one-hot per categorical column.

## Case table: `data/cases.csv`

One row per incident or scenario in the article's Tables 1-7, with the author claim, an independent source URL **only if one was opened or returned by a search
in this work**, an incident-evidence status, a separate AI-use evidence status, and observed-versus-hypothetical impact. Regenerate with `python data/build_cases.py`.
Rules: a case is context, not a labelled sample; no model label is derived from it; no interview text is invented. Where independent support is missing the row says so.
